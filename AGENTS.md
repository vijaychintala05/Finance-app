# Codex workflow for FirmBooks

The active Codex Goal, when present, defines **what** to accomplish. This file defines **how** to do repository work. Preserve the Goal and existing user instructions. Classify each meaningful task internally as LOW, MEDIUM, HIGH, or CRITICAL before implementation; do not ask the user to classify it. The 70–80% Luna / 20–30% Sol target is guidance, not a quota. Correctness and reliability win whenever the two conflict.

## Model routing

- GPT-6 Luna is the normal worker. Use it for focused exploration, established implementation patterns, UI, forms, tables, CRUD, routine APIs, tests, type/lint fixes, documentation, and straightforward debugging. Raise Luna's reasoning effort for a demanding worker task before escalating routine work.
- `sol_architect` is GPT-6 Sol at high reasoning, normally read-only. Request it for architecture, schema/migrations, data models, transactions, concurrency, caching, authentication, RBAC/permissions, security, approvals, audit, API contracts, shared infrastructure, cross-module design, difficult bugs, performance architecture, financial/accounting logic, data integrity, or unclear invariants. Give it focused findings from Luna's exploration.
- `sol_reviewer` is GPT-6 Sol at high reasoning, normally read-only. It reviews the actual diff and surrounding code, tests, and acceptance criteria after implementation. Its `PASS` is required for HIGH and CRITICAL work, and for MEDIUM work affecting persistent data, financial information, permissions, shared backend logic, reusable APIs, multiple modules, or material regression risk.
- Use the two named Sol agents when available. Ordinary spawned workers default to Luna. Do not ask the user to change models or approve handoffs between these stages.
- If the client cannot launch a required named Sol specialist, report that limitation and do not claim a HIGH or CRITICAL task passed its review gate. Project instructions route work but do not enforce a token-use percentage.
- The trusted-project `.codex/config.toml` supplies defaults for new sessions; changing it does not switch the model of an already-running session. Explicit user, client, or managed-policy overrides and model availability can supersede those defaults.
- Custom roles in `.codex/agents/` make the Sol specialists discoverable with their pinned model and reasoning settings. `AGENTS.md` describes when to use them, but the client remains responsible for orchestration; never report a Sol gate as satisfied unless that specialist actually ran and returned the required result.

## Risk and execution gates

- **LOW**: CSS, copy, isolated UI/forms, routine CRUD, docs, lint/type fixes, and small test updates. Luna investigates, implements, and runs affected checks. Escalate if critical logic appears.
- **MEDIUM**: several-file features, frontend plus backend, shared UI, established new API patterns, moderate refactors, or important app behavior. Luna investigates and makes a brief plan, implements, and runs affected unit/integration tests. Use Sol review for the risk conditions above.
- **HIGH**: database/schema/migrations, backend architecture, auth, permissions, API contracts, shared financial logic, large refactors, transactions, concurrency, approval or audit systems. Luna maps relevant code, `sol_architect` approves the design and invariants, Luna implements and tests, then `sol_reviewer` reviews the actual patch. Fix blocking findings, rerun relevant tests, and get `PASS` before declaring completion.
- **CRITICAL**: core accounting/posting/reversals, double entry, ledgers, AR/AP or customer/vendor balances, statements, bank reconciliation, transaction atomicity, potential financial corruption, auth/authorization architecture, production migrations/destructive database operations, core permissions, or critical cross-module design. `sol_architect` defines the design and invariants first; Luna inspects exact sites and implements; run unit, integration, regression, financial-integrity, and permission/security checks as relevant; `sol_reviewer` performs a deep review. If it finds a conceptual flaw, return to `sol_architect`, correct it, retest, and obtain a final `PASS`.

Escalate promptly to `sol_architect` if two genuine worker attempts fail on the same root problem, the same test still fails after two fixes, the root cause or architecture is unclear, patterns conflict, undocumented rules appear, scope expands substantially, or the work touches unexpected database, security, financial, transaction, or concurrency behavior. Include the requirement, relevant files, known architecture, suspected cause, attempted fixes, exact errors, failing tests, and unresolved decision. Do not make speculative changes or loop indefinitely.

## Repository invariants

PostgreSQL and the posted general ledger are authoritative; the browser must not simulate successful financial writes. Enabled writes are tenant-scoped, authenticated, permission-checked, idempotent, and audited. Financial source documents, balanced journals, account balance cache, and audit events commit in one transaction. Posted records are immutable; corrections use linked reversal journals. Every journal entry balances to the cent, and each line carries one positive debit or credit. Period/account locks, exact minor-unit money conversion, duplicate-posting prevention, and server-derived reports remain intact. Consult [README.md](README.md), [DESIGN.md](DESIGN.md), and [docs/ACCOUNTING_ENGINE.md](docs/ACCOUNTING_ENGINE.md) when the change touches their domain.

## Verification and completion

Start with the smallest relevant tests and broaden according to risk. For critical financial changes, consider zero/negative amounts, decimal precision and rounding, retries and duplicate actions, partial failures, reversals, lifecycle states, voided history, concurrency, old data, and permission boundaries. The package scripts are `npm run lint`, `npm test`, `npm run build`, `npm run test:e2e`, and `npm run test:postgres`; use the subset justified by the change, plus required release gates. A passing test is not proof of an invariant the test does not cover.

Before completion, compare the original requirement with the actual implementation. Check real backend wiring, authoritative data, loading/empty/error states, persistence, permissions, responsive behavior when relevant, and regressions. Do not claim completion for UI-only placeholders, missing integration, unvalidated migrations, failing important tests, unresolved review blockers, or unmet acceptance criteria. Report genuine platform or environment limitations honestly. Keep Sol's context focused: pass the requirement, relevant code and schemas, plan or diff, test changes/results, and unresolved questions rather than asking it to rediscover unrelated repository areas.
