## Problem Statement

The owner currently records roughly 50–100 transactions each month and spends about two hours entering them. They previously used Zoho and expect the Banking module to make a bank statement useful: import the bank's report, match lines already recorded in FirmBooks, and explicitly add any missing entries so none are overlooked. The owner is the current user; a CA may use the product later.

Today, posting a transaction to a bank ledger account does not make it appear in the Banking account workspace. The workspace reads imported statement rows only. This preserves the difference between bank evidence and book records, but the product has no visible bank-book register and the match suggestions endpoint does not discover candidates for the real UI call. As a result, the customer cannot complete the statement-to-books workflow they expect.

## Demand Evidence

- Current use is firsthand: the owner records their own business transactions in FirmBooks.
- The manual entry volume is estimated at 50–100 transactions per month.
- The owner estimates the task takes about two hours monthly.
- The owner has used Zoho and points to its statement import and matching workflow as the reference.
- No paying customers or independent user observations have been reported. The CA workflow is a future possibility, not a current acceptance requirement.

## Status Quo

The owner manually enters transactions into FirmBooks. The app's existing import flow can store statement evidence, but the workspace does not show the posted book movements alongside it and the matching drawer has no server-discovered suggestions. This leaves the user without a complete workflow for checking that every bank line has a corresponding book entry.

Zoho's documentation describes imported bank lines being matched against transactions already in the books, categorized when no existing record applies, and then included in a distinct reconciliation step. Its import workflow also previews/matches file columns before import. These are workflow references only; FirmBooks should retain its own posting controls and data model. [Zoho matching guide](https://www.zoho.com/uk/books/help/banking/matching-transactions.html), [Zoho statement import guide](https://www.zoho.com/in/books/help/banking/add-transactions.html), [Zoho reconciliation guide](https://www.zoho.com/us/books/help/banking/reconciliation.html).

## Target User & Narrowest Wedge

**Current user:** the business owner recording their own transactions.
**Wedge:** import one bank statement, see every line, match lines to already-posted book movements, explicitly create a missing accounting transaction for unmatched lines, and finish only after each line is resolved and the statement-to-book difference is explained.

The CA role should be supported by durable organization-scoped records and audit history, but dedicated CA onboarding, multi-client workspaces, and collaboration tools are outside the first implementation.

## Constraints

- No live bank connection or credential collection in this scope.
- PostgreSQL and posted general-ledger entries remain authoritative. The browser must not create synthetic bank statement rows or simulate successful posting.
- An import adds immutable statement evidence and audit/observation data. It does not itself post a journal, payment, expense, tax, or balance change.
- Matching an existing book movement changes reconciliation links/status and audit history only.
- Creating an accounting entry from a statement line requires an explicit review and confirmation, and uses the server posting engine and its existing tenant, permission, period-lock, balance, and audit protections.
- Suggestions are recommendations. Users confirm matches and categories; uncertain amounts, duplicates, and unmapped columns remain visible exceptions.
- Use the statement file from the user's actual bank to validate support before promising broad format coverage. Current UI accepts CSV/XLS/XLSX while backend parsers expose additional formats; the bank and exact report format have not yet been identified.
- Keep all work behind existing financial capability and permission gates. Never bypass optional-feature certification.

## Premises

1. Every imported statement line must remain visible and be imported at most once for the same account and source evidence.
2. Every line must be matched to posted books, explicitly added to books, or placed in an auditable exception state before a period can be closed as reconciled.
3. Book movements and imported statement evidence are separate sources. Do not copy ledger postings into the statement feed or imply that a posted book transaction proves the bank processed it.
4. Automatic bank linking is excluded. File import is the bank-data source for this workflow.
5. The user values completeness and reviewability over silently auto-posting or auto-matching uncertain transactions.

## Cross-Model Perspective

The Luna code exploration and Sol architecture review independently confirmed the core gap: `BankAccountWorkspace` maps only statement rows, `getWorkspace` selects only `bank_statement_transactions`, and the UI's GET suggestions call reaches a service with an empty candidate list. Sol also identified critical integrity risks in the existing categorize and reconciliation completion paths; those must be fixed before calling the workflow reliable.

## Approaches Considered

### Approach A: Minimal visibility patch

Add a list of posted bank-ledger journal movements to the workspace and keep the existing import/match path mostly intact.

- Effort: M
- Risk: High if the list is mistaken for statement evidence or if current matching/finalization defects remain.
- Pros: Quickly makes posted activity visible; reuses existing ledger queries.
- Cons: Does not deliver the owner's requirement to resolve every line; match suggestions still need real server candidates; existing cache and reconciliation defects make results unsafe.
- Reuses: `journal_lines`, `journal_entries`, `bank_accounts.ledger_account_id`, `BankAccountWorkspace`.

### Approach B: Complete file-based reconciliation workflow (recommended)

Keep statement and book records distinct, build an authoritative bank-book register, discover and confirm matches on the server, explicitly create missing accounting transactions, and make reconciliation close atomic and based on both sides. Repair existing cache and status math defects in the same work.

- Effort: L/XL
- Risk: Medium after architectural review and concurrency testing; High until book movement identity and historical match compatibility are resolved.
- Pros: Directly addresses the two-hour monthly task and the user's “not miss anything” requirement; keeps posted books authoritative; produces a usable workflow without connecting to a bank.
- Cons: More than a screen change; requires server query/API work, robust allocation identity, transaction locks, migration compatibility review, and PostgreSQL concurrency coverage.
- Reuses: Existing import preview/confirm, parser factory, fingerprints and observations, posting engine, tenant/permission middleware, reconciliation tables, banking drawers, and feature gates.

### Approach C: Import-first with manual resolution only

Improve file preview and line visibility, then require the user to search books and create missing entries manually without automatic suggestions.

- Effort: M
- Risk: Low to medium.
- Pros: Conservative and simple; never relies on weak match confidence.
- Cons: Preserves much of the two-hour manual workload; does not meet the user's explicit request to match transactions like their prior Zoho workflow.
- Reuses: Existing statement import and explicit categorize/create-from-statement actions.

**Recommendation:** Approach B. It is the only option that meets the stated completeness goal while preserving the accounting trust boundary. Match automation should suggest; the user should confirm.

## Recommended Approach

### App-wide integration boundary

Treat this as shared financial behavior, not a Banking screen feature. The bank-book register is a server-side projection of every posted movement on the selected bank ledger. Reuse the central journal/posting path so payments/receipts, expenses, vendor settlements, transfers, manual journals, reimbursements, gateway settlements, asset activity, and reversals appear through their existing posted `journal_entries` and `journal_lines`. Extend individual source modules only when their posting path bypasses the shared ledger or fails to identify the bank ledger correctly; do not add duplicate banking-feed writes to each module.

Keep the rest of FirmBooks consistent through the General Ledger as the shared source: a bank transaction posted from any existing module remains available to account balances, dashboards, cash-flow and financial reports, audit history, and period controls under current ledger rules. Importing a statement must not change those app-wide book totals. Explicitly creating a missing accounting entry from a statement line must use the normal posting engine so it appears consistently across those existing areas after commit. Reversals remain linked journal entries and visible in history; they never erase the original movement.

| Existing app area | Integration rule |
| --- | --- |
| Sales receipts/advances/refunds, vendor payments/advances/refunds, expenses, reimbursements, transfers, manual journals, treasury, gateway settlements, fixed assets, recurring activity, and reversals | Bank register reads each resulting posted bank-ledger journal line; no parallel statement-feed row is written by source workflows. Verify each path reaches the canonical posting engine and the selected bank ledger. A shared journal for a payment and advance must appear as the correct movement once, with source links enriched without duplicate rows. |
| Banking import and match | Statement evidence remains separate. Match links point to a stable bank-ledger movement. Create-from-statement uses standard posting. Source edit/void/reverse guards must recognize the canonical movement and legacy source-document aliases so matched activity cannot be changed behind the reconciliation. |
| Chart of accounts, bank balance cache, dashboards, cash flow, and financial reports | Continue to derive from posted GL/cache. A shared reconciliation-status projection must feed Banking, the home dashboard, accountant overview, period-close checks, and bank reports so categorized/reconciled/ignored/partial states are counted consistently and statement-vs-book cutoffs align. Do not count imported evidence as revenue, expense, or cash a second time. |
| Audit, permissions, tenant isolation, period close, reversal and reopen | Keep the same authenticated tenant and RBAC boundaries; persist posting, allocation, audit, source guards, and close state atomically. |

### User workflow

```text
Choose bank account
  -> Import report file
  -> Preview mapped columns, dates, amounts, duplicates, and balance checks
  -> Confirm import (immutable statement evidence only)
  -> Review all imported bank lines
       -> Confirm one or more posted book movements as a match
       -> OR explicitly create/post the missing accounting transaction
       -> OR leave an auditable exception with a reason
  -> Review outstanding book movements and statement/book difference
  -> Close reconciliation for the statement period
```

### Data model and authoritative query

Keep `bank_statement_transactions` as imported bank evidence. Add a server-derived book register sourced from posted journal entries and journal lines associated with the selected `bank_accounts.ledger_account_id`. The DTO must identify the journal and source-document context, movement direction, date, amount, reference, counterparty where available, and reversal status. Never manufacture a statement row for a book movement.

Before matching, establish a stable identity for each movement on the bank ledger. A journal may contain more than one line against the same bank account, so matching must not aggregate unrelated lines into one candidate. Review existing document-level matches and migrate/map history only when a movement can be identified unambiguously; surface ambiguous history for repair instead of guessing.

### Matching and missing entries

Candidate discovery must happen server-side within the authenticated organization and selected bank ledger. Consider only posted, unreversed movements in the correct currency and compatible bank direction. Score exact amount, reference, date proximity, and counterparty/narration as suggestions. Show the reasons and allow the user to reject a suggestion or select another candidate.

Support partial/split matching only with an allocation record that locks and checks both statement and book-movement remaining capacity. Concurrent imports or users must not allocate beyond either side. Retries must be idempotent. Invoices and bills are not bank cash movements by themselves; a payment posting is the bank movement. Matching must not mark an invoice/bill as cash-cleared without the corresponding payment workflow.

For a genuinely missing book entry, offer an explicit create action from the statement line. Collect required account/category, date, amount, and available counterparty/reference/tax information; validate permissions, tenant ownership, currency precision, active accounts, and period locks on the server. Post through the existing financial posting service in one database transaction with its source document, journal, cache, reconciliation allocation, and audit event.

### Reconciliation and accounting correctness

Fix the duplicate `bank_accounts.current_balance` increment in categorize flow: the posting engine already updates that cache. Add a regression proving one categorized posting changes the GL and cached balance by the same amount.

Rework summary and close semantics so categorized/created transactions are recognized as posted book movements rather than counted again as unmatched statement amounts. Duplicate, ignored, partially matched, and exception rows must not be silently treated as fully matched.

Use one sign convention throughout: statement credits increase the bank balance and statement debits reduce it; bank-ledger debits increase the book balance and bank-ledger credits reduce it. Statement ending balance is opening statement balance plus statement credits minus statement debits. Book ending balance is opening GL balance plus posted bank-ledger debits minus posted bank-ledger credits, through the same cutoff date. Identify statement-only entries and book-only entries separately; valid outstanding book deposits/withdrawals are carried forward as timing items in the adjusted balance calculation, not marked as statement matches. If a statement omits its opening balance, derive it from the prior verified statement close only when the dates are contiguous and there is no gap; otherwise require a reviewed opening balance/statement range before close, and show the source of that balance.

Use this disposition policy for each statement period:

| Statement row disposition | May close? | Balance treatment |
| --- | --- | --- |
| Fully matched to posted book movement(s) | Yes | Count statement and allocated book movement once on their respective sides. |
| Explicitly added/posted from this statement row | Yes | Count statement movement and resulting posted book movement once each. |
| Duplicate of another imported row | Only after user confirms and links it to a canonical row | Exclude the duplicate observation from movement totals; canonical row still requires resolution. |
| Ignored non-transaction export artifact | Only after user confirms with a reason and evidence; never for a real bank movement | Exclude only the proven artifact; retain raw evidence and audit decision. |
| Partial allocation, invalid row, unresolved exception, or real line ignored without an allowed reason | No | Keep visible and block period close. A partial line becomes close-eligible only when allocations total the full statement amount or the remainder is explicitly resolved through an allowed disposition. |

Calculate and finalize reconciliation under a transaction with consistent locking of the bank account, statement rows, book allocations, and period boundary. Persist session membership, cutoff date, opening/closing balances, outstanding book items, difference, dispositions, state transitions, and audit event atomically. A zero balance difference alone is not proof that all lines are resolved. Set `reconciled_through_date` only when the explicit close invariant passes; reopening must use the existing permission and an audited state transition.

### Import completeness and user experience

Preview must report file parsing errors, unmapped columns, invalid/duplicate rows, exact and possible duplicates, row counts, statement date range, currency, opening/closing balances, and any arithmetic discrepancy before confirmation. Persist original import evidence and per-row observations. Ensure UI pagination, filters, tab counts, and search are server-backed so more than 50 rows do not disappear from counts or filtering.

The account workspace should clearly distinguish **Statement lines** from **Transactions in FirmBooks**, with separate statuses and loading/empty/error states. Use a visible exception queue for unmatched, duplicate, invalid, and partially matched rows. Closing shows the unresolved row count and difference with links back to the items that need action.

### Phased delivery and release gates

Do not ship new matching UI ahead of server-side integrity controls. Deliver sequentially:

1. **Preflight:** identify the first bank and sanitized file; characterize active/historical match identities; document gates, permissions, and rollback. Block launch if active historical matches cannot remain unambiguous.
2. **Read-only register and real suggestions:** add server-authoritative posted movement reads, candidate discovery, distinct statement/book views, and server-backed counts/search. No new match write path is enabled yet.
3. **Safe match allocations:** add stable movement identity, additive allocation schema, locks, exact remaining-capacity checks, idempotency, unmatch/reversal lifecycle, and backward-compatible history handling. Pass PostgreSQL concurrency tests before enabling.
4. **Explicit missing-entry creation and categorization repair:** post through the existing engine in one transaction, remove the redundant cache increment, and prove source, journal, GL, cache, reconciliation link, and audit consistency.
5. **Import-to-close completion:** validate the first real file format, preview/control totals, row disposition policy, outstanding-book math, atomic close/reopen, permissions, and a representative 50–100 row workflow before enabling close.

**Launch blockers:** all five increments, Sol architecture approval and final Sol review, real-PostgreSQL transaction/concurrency tests, and one sample-validated initial format. Keep the feature gate off if migration, permission, posting, or reconciliation invariants fail. Rollback disables the new feature gate and retains allocation/history evidence; it never deletes or rewrites posted journals or audit records.

## Success Criteria

- The selected bank account shows all posted book movements from its ledger across existing app transaction workflows, clearly separated from imported bank evidence; drafts, other tenants, other bank ledgers, duplicate source aliases, and invalid reversal state do not leak into the register.
- The initial launch accepts only the bank/file format validated against a sanitized real sample. Other formats remain explicitly unsupported until separately validated. Preview reports row counts and control totals only when those values are present and verified for that format.
- Every imported line remains visible and reaches a clear matched, explicitly added, ignored-with-reason, duplicate, or unresolved-exception state. Close is blocked while unresolved required items remain.
- The user can confirm correct suggestions and explicitly add missing transactions; no import or suggestion silently posts financial entries.
- Matching and creation persist across refresh and are idempotent under repeated requests. Parallel match attempts cannot over-allocate a statement line or book movement.
- After one create/categorize action, journal, GL account balance, bank balance cache, reconciliation state, and audit history agree to the cent.
- Dashboard banking attention, accountant overview, period close, cash-flow and bank reports agree on the same status definitions and cutoff dates; statement evidence alone never changes posted-book totals.
- Matched bank movements cannot be edited, voided, or reversed through their source modules without the existing authorized unmatch/reopen path and linked reversal lifecycle.
- Period close and reopen are atomic, permission-checked, auditable, and correct with outstanding book movements, fees, partial matches, duplicates, and reversals.
- On a representative 50–100 row statement, the owner can account for every line and identify exceptions without manually re-entering already-posted transactions. Measure elapsed time against the current approximate two-hour monthly baseline.
