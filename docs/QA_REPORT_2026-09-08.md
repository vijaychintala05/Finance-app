## Confirmed current defects and blockers

Severity: **P1** affects accounting integrity, authorization/trust, or release viability. **P2** is a significant product/integration failure.

### QA-01 — P1: public portal accepts an unverified payment and changes the AR subledger without a journal

`POST /api/v1/public/portal/:token/pay` accepts only an amount, method label, and reference. It does not use the gateway service or require provider confirmation. The probe received HTTP 200 and `success: true`, then found a `PAID` payment with no `journal_entry_id`. AR aging became 0 while GL receivables remained 100.

This makes a public bearer-token request an accounting posting authority and creates a subledger/GL mismatch. The same flow updates invoice state directly and catches allocation insert failures. Source: `CustomerPortalService.ts:243–350`, public route at `index.ts:87`.

### QA-02 — P1: sales-order remaining balance cannot be invoiced after a partial invoice

Create a 100 confirmed sales order, invoice 40, then convert the remaining amount without supplying another explicit partial amount. Expected second invoice: 60. Actual: rejection, **“Invoice amount exceeds the uninvoiced sales order balance.”**

The method chooses remaining amount 60 but reuses the original 100 line items unless `partialAmount` is supplied. Source: `SalesEngine.ts:905–992`.

### QA-03 — P1: purchase-order remaining balance cannot be billed after a partial bill

Create a 100 approved PO, bill 40, then convert the remaining balance. Expected second bill: 60. Actual: transaction fails, **“Journal is unbalanced: debit=100.00, credit=60.00.”**

The remaining bill carries the original 100 line items while its header/credit is 60. Source: `PurchasesEngine.ts:611–687`.

### QA-04 — P1: receiving does not track completion and accepts duplicate full receipts

Receiving a full 100 PO leaves it `PARTIALLY_RECEIVED`; submitting a second full receipt is accepted. `receivedAmount` is not accumulated or checked against the order, and full completion is never reached. This allows duplicate receiving records and unreliable fulfillment state. Source: `PurchasesEngine.ts:696–775`.

### QA-05 — P2: journal drill-down loses document identity after invoice revision

Before revision, the original invoice journal drills down as `INVOICE`. After a successful invoice revision, the same original journal becomes `MANUAL_JOURNAL`; its date is returned as `Sun Mar 01` rather than ISO `2026-03-01` in the memory-backed reproduction. The lookup only matches the invoice's current posting and reversal pointer, not the original journal linked through reversal history. Source: `DrillDownService.ts:63–83`, `260–290`.

### QA-06 — P2: Stage 6 frontend calls do not match mounted API routes

The document UI requests `/api/v1/stage6/inbox?limit=50`; the live local server returns HTTP 200 **HTML for the React application**, while `/api/v1/documents/inbox?limit=50` returns the expected JSON. Similar mismatches exist for upload/OCR/conversion, portal-token management, and migration calls:

- UI `/stage6/inbox...`; API `/documents/inbox...`
- UI `/stage6/portal/tokens`; API `/portal/tokens`
- UI `/stage6/migration/opening-balances`; API `/migration/opening-balances/post`
- UI `/stage6/migration/master-data`; API `/migration/import`

Service-level Stage 6 tests therefore pass without proving the UI workflows. Sources: `DocumentInboxView.tsx:78–211`, `CustomerPortalView.tsx:234–254`, `DataMigrationModal.tsx:115–185`, `stage6.routes.ts`.

### QA-07 — P1: upload/OCR presents fabricated values as extracted data

The UI reads the selected file but discards its contents, stores a synthetic `storage.firmbooks.local` URL, and sends generated mock invoice text based on filename and file size. Independently, the OCR service turns an empty `receipt.pdf` into a USD 150 Acme invoice with **0.94 confidence**. A reviewed conversion can then create a financial document from invented data.

Sources: `DocumentInboxView.tsx:97–132`, `DocumentOcrService.ts:205–283`. Probe: “OCR does not invent an amount when no content is supplied”.

### QA-08 — P1 production risk: recovery manifest omits the new feature state

`POINT1_RECOVERY_SCHEMA` ends with recurring transaction occurrences. It does not include the new sales orders, purchase orders, receipts/delivery state, background jobs/runs, gateway events, bank-feed connections, document inbox, saved views, or portal tokens. A recovery artifact can therefore validate successfully while omitting material Stage 2/5/6 state. Source: `recovery/schema.ts`.

### QA-09 — P2: several Stage 5 services remain unreachable in normal runtime

The email outbox worker starts in `initDatabase`. Caller searches found no runtime worker loop for `JobSchedulerService`/`RecurringDocumentJobHandler`, and no mounted bank-feed or payment-gateway endpoint. The corrected internals are not yet a usable customer flow.

### QA-10 — P1 security risk: portal bearer tokens remain stored in recoverable form

Schema now adds `token_hash`, but `CustomerPortalService` still inserts and queries the raw `token` column. Database access would expose active public portal credentials directly. Source: `CustomerPortalService.ts:53–97`; additive schema in `usabilitySchema.ts`.
