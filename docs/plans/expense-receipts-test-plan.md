# Expense Receipt Acceptance Tests

Generated by autoplan engineering review, 2026-08-31, main. Planned checks, not completed results. Use synthetic receipt images and an isolated organization/database; preserve the user's running demo.

## Pages and Routes

- `/#/expenses`: Record Expense, expense cards/table actions, receipt count, saved details.
- `POST /api/v1/finance/expenses`: optional receiptImages and atomic posting.
- `GET /api/v1/finance/expenses/:id/receipts/:receiptId`: authorized image retrieval.
- Existing organization backup/export and isolated restore flow.

## Critical Journey

1. Banner absent on desktop and mobile. Record Expense reachable by mouse and keyboard.
2. Enter financial details, attach real JPEG/PNG/WebP, inspect full prepared image; remove and reselect without losing fields.
3. Submit once; one expense, one balanced posting and the selected receipt set persist. No success before commit.
4. Reload page, reopen expense by keyboard, load full image and download/open successfully. Browser reports naturalWidth > 0 and receipt text remains legible.
5. Reverse an expense; original receipt evidence remains available to authorized users.

## Boundaries and Failures

- No attachment; 1 and 3 valid files; 4 selected; unsupported PDF/HEIC/SVG; empty file; truncated image with valid signature; MIME mismatch; invalid base64; long/unsafe filename.
- Each prepared image <= 900 KiB; combined <= 2 MiB; one byte over each cap; original > 10 MiB; excessive decoded pixels; decode/canvas failure. Reject before posting where possible; preserve valid selections and draft.
- Account refresh during typing; modal close during image preparation; organization switch; close/reopen details before fetch resolves; logout. No draft erasure from refresh, cross-tenant preview or leaked object URLs.
- Double click; delayed upload; server validation error; network loss before and after commit; retry unchanged payload with identical idempotency key; list-refresh failure after committed save. No duplicate expense or false rollback claim.
- Inject receipt insert, journal and audit failure after expense insertion; all transactional writes roll back together.
- Missing login, insufficient permission, other organization, wrong parent expense and missing receipt. No image leakage; nondisclosing 404 where required; no public cache.
- One image fetch fails while others succeed: finite loading, explicit retry, working images retained.
- Real server using documented JSON_BODY_LIMIT: valid maximum request accepted; oversized request receives useful 413. Check reverse-proxy limit separately.
- Backup/restore round trip: receipt IDs, tenant/expense association and decoded byte content unchanged; old schema backups handled explicitly. No child-FK deletion failure.
