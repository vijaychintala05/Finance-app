# PDF Template Variant Audit

## Scope and reading rules

Source reviewed: `server/src/services/DocumentPdfService.ts`, `server/src/database/documentTemplateSchema.ts`, `server/src/services/DocumentTemplateService.ts`, `src/components/settings/PdfTemplatesSettings.tsx`, `server/src/tests/pdfTemplateSettingsAcceptance.test.ts`, `server/src/tests/documentPdfRegistry.test.ts`, and `src/__tests__/brandingSettingsStudio.test.tsx`.

`DOCUMENT_PDF_CATALOG` contains 44 renderer-accepted IDs. The settings gallery independently exposes 44 versioned `modelId`s. They are not the same ID inventory. A registered settings model is resolved by model ID, and its `layoutFamily` takes precedence over the renderer's hard-coded `layout(id)` fallback. Unregistered catalog IDs use the hard-coded fallback when accepted. The table lists both, in category order; the settings IDs are not asserted to be one-to-one equivalents of the catalog IDs.

The renderer has three general visual branches, not 44 independently implemented designs:

| Branch | Rendered difference |
| --- | --- |
| `standard` | Filled primary-color header band; prints document title, literal `Template: <templateId>`, number and status. |
| `ledger` | Thin primary rule, larger title, number, and a formal-record/status band; does not print template ID. |
| `compact` | Short accent-color header strip with title and number; does not print template ID. |

All keep category-driven issuer/party metadata, tables, totals, notes, signatures, and footer unless the category/field branches below say otherwise. The registry also supplies preset `templateTitle`, so two IDs in the same layout family can differ in title. A user-saved title/configuration can override the preset. No claims below are inferred from gallery labels or descriptions.

## Variants and duplicate behavior

- Explicit model-ID payload/layout branches now include the six statement variants, invoice `pos` (item/quantity/amount table), payment receipt `cash-receipt` (amount-forward summary), expense `project-billable` (linked project/client recovery and stored billing amounts), and all three credit-note variants: formal memo (`statutory`), active invoice-application ledger (`goods-return`), and value-first adjustment slip (`adjustment`). These remain a small subset of the non-statement catalog.
- For non-statements, IDs select at most `standard` / `ledger` / `compact` presentation and a preset or saved title. They do not select the specialized fields advertised by several gallery descriptions (export, jobwork, matching, cheque, contract, returns, reimbursement, etc.). Category-wide source data drives the same table and totals.
- Quotes `milestone-proposal`, delivery challans `packing-list`, and invoices `export` now have model-specific header compositions despite sharing a registered layout family with another model. The remaining standard/ledger/compact branches still reuse common body composition. Distinct titles, model IDs, and colors alone do not prove distinct document content.
- Several catalog and settings IDs with the same spelling still choose different families because the registered model family overrides fallback: `dispatch` (catalog compact vs model standard), `jobwork` (catalog ledger vs model compact), `requisition` (catalog ledger vs model compact), `adjustment` (catalog standard vs model compact), `matching` (catalog ledger vs model compact), `standard` (category-specific fallback vs model-specific selected family), and `ledger` for journals (catalog ledger vs model compact). This is a material reason not to infer output from ID names.
- Most non-statement model IDs still have no renderer branch keyed to their settings model ID. Distinct preset titles are data/configuration, not distinct field layouts; verified exceptions include invoice `pos` and `export`, quotes `milestone-proposal`, delivery challans `packing-list`, payment receipt `cash-receipt`, expense `project-billable`, and the three structurally distinct credit-note layouts. Gallery copy is not renderer evidence.

## Settings behavior updated in the current working tree

The following settings now have renderer reads and focused output assertions:

| Key | Category | Current behavior and limitation |
| --- | --- | --- |
| `showScopeOfWork` | Quotes, sales orders, purchase orders | Hides the document notes/terms block when disabled. There is not yet a distinct milestone or structured scope field, so this currently hides all notes/terms, not just a separately modeled scope section. |
| `showPackageDetails` | Delivery challans | Shows or hides the Packages column in rate-hidden and normal challan tables. Package weights are not available and are not claimed by the control. |
| `showAccountAllocation` | Bills | Shows a Posted General Ledger Allocation table from the bill's linked journal lines, with debit and credit columns. No unposted accounting allocation is inferred. |
| `showExpenseCategory` | Expenses | Resolves the tenant-scoped expense account name and displays it as the category. |
| `showTdsDeduction` | Expenses | Displays TDS as a negative deduction when the persisted expense has TDS; Net Paid reflects the bank credit. |
| `showPaidStamp` | Invoices | Displays PAID IN FULL only when the server-side source status is PAID and the balance is zero or lower. |
| `showPayablesLedger` | Vendor credits | Controls the existing Remaining Credit / Balance Due row. It is not a vendor-payment ledger posting summary. |
| `project-billable` model | Expenses | Adds project/client recovery details, stored client charge/markup and source-backed pending/posted invoice status. Invoice reference is displayed only from a tenant-scoped linked invoice row. |

The UPI QR and reimbursement-status controls were removed because no supported VPA/QR source or reimbursement-status field is presently modeled for this document-PDF path. The E-Way Bill control label no longer claims a barcode. The legacy `showReimbursementStatus` config key remains accepted for old records, but it is not exposed by the current UI.

Expense PDF totals now use exact-cent presentation rules aligned with `ExpensePostingService`: exclusive `amount` is the base, inclusive `amount` includes its tax, RCM tax is labeled as not paid to the vendor, TDS is a deduction, and Net Paid matches the bank credit. No accounting posting behavior was changed. Preview watermarks are drawn on every buffered page, and notes advance by measured rendered height.

## Remaining renderer and evidence gaps

- Sales-order, purchase-order, bill, and vendor-credit registered models now have source-backed summary panels with distinct facts. The bill panels preserve total-only persisted bills and the vendor-credit panels omit disabled fields completely. A6 landscape long-value coverage checks the panels stay within page bounds while full details remain in ordinary sections. The gallery lazily renders page one of each visible model's server PDF onto a canvas, and the full preview renders every PDF page with PDF.js; desktop and mobile browser checks verified visible content under the production-safe canvas approach.
- The Zoho-inspired settings editor now exposes the renderer's existing paper size, orientation, font, and saved per-template colors; gallery sheets use the saved title/colors, while Preview opens the actual server-rendered PDF. Light colors receive contrasting text on filled PDF panels and dark fallback ink on white/pale panels. The focused acceptance suite renders compact tables, statement balance tiles, and the three special headers with a white theme.
- The 44 IDs are still not 44 distinct document-specific designs. Several variants now have source-backed body panels, but quotes, delivery challans, invoices, receipts, expenses, vendor payments, and journals retain generic siblings. Gallery preset titles do not prove unique content/layout. The matrix above identifies unsupported fields/layouts.
- Gallery descriptions have been brought back in line with supported fields and the available standard/ledger/compact families. Most non-statement template IDs still lack model-specific content structures, and layout-family differences alone do not satisfy the requested 44 purpose-built templates.
- `showScopeOfWork` currently suppresses all notes/terms in its categories; split structured scope from ordinary notes before treating this control as a finished Zoho-style field editor.
- `showAgingBuckets` remains removed. Do not fabricate aging data.
- The acceptance suite additionally asserts project-billable customer/client resolution, pending vs posted invoice state, tenant isolation, full long-name/reference layout and untruncated large stored charge; all three credit-note issuance variants/default with byte retrieval, invalid amount/status and negative remaining rejection, cross-tenant/missing/unposted/reversed journal rejection, audit-failure rollback, posted applications, repeated invoice links, reversed/status-inconsistent row filtering, service-recorded refunds, and fully used/reversed lifecycle states; 4,000-character titles remain single-line in all three layout families on A6; reconciled persisted receipt allocations and exact zero formatting at the formatter boundary (persisted payments remain positive by schema); exact marker/reference/balance output for all six live statement variants; and all six order and six bill/vendor-credit panels. It still does not compare all 44 model outputs individually.
